# BuildOS: архитектура первого этапа

Приложение — модульный монолит. Next.js обслуживает UI и HTTP API, Prisma работает с PostgreSQL. У приложения одна кодовая база и один процесс сервера; бизнес-модули отделены друг от друга.

```text
src/
  app/
    page.tsx                      интерфейс и демо-вход
    error.tsx                     граница ошибок React
    api/
      workspace/route.ts          чтение рабочего пространства
      workspace/commands/route.ts запись операций
      ai/route.ts                 ответы mock AI по данным базы
      health/route.ts             проверка подключения и схемы
  modules/
    shared/types.ts               DTO интерфейса, роли и состояния
    company/                      демо-контекст, права, приглашения
    tenders/                      создание, анализ, преобразование
    projects/                     проверка принадлежности проекта
    field/                        дефекты, задачи, отчёты, документы
    procurement/                  заявки из рекомендаций
    ai/                           mock-анализ и контекстные ответы
    workspace/                    контракты API, оркестрация, чтение, клиент
  server/
    config.ts                     проверка серверных настроек
    db.ts                         единый Prisma Client
    http/                         лимит тела запроса и формат ошибок
  lib/
    domain.ts                     совместимые экспорты для UI
    i18n.ts                       рус/каз/англ
prisma/
  schema.prisma                   модели PostgreSQL
  migrations/                     история изменений схемы
  seed.ts                         воспроизводимые начальные данные
tests/
  unit/                           контракты, ошибки, права
  integration/                    реальные транзакции PostgreSQL
```

## Путь запроса

1. UI вызывает общий API-клиент. Полное состояние приложения больше не отправляется на сервер.
2. HTTP-обёртка читает JSON с ограничением размера и проверяет структуру через Zod.
3. Сервер создаёт контекст компании. В первом этапе компания берётся из `.env`, а не из тела запроса.
4. Проверяются права выбранной демо-роли на запись.
5. Оркестратор вызывает соответствующий бизнес-модуль в транзакции Prisma.
6. Чтение возвращает согласованный снимок данных компании из PostgreSQL.
7. UI обновляется ответом сервера. Ошибки имеют HTTP-статус, код и идентификатор запроса.

## Целостность данных

- Составные внешние ключи включают `companyId`. Нельзя привязать задачу одной компании к сотруднику другой.
- Этаж связан с блоком внутри того же проекта и компании; дефект и задача — с этажом своего проекта.
- Финансовые значения хранятся как `Decimal`, а не `Float`. Для отображения DTO преобразует их в число; будущие финансовые расчёты должны использовать Decimal.
- Преобразование тендера создаёт проект, блок, этажи, зоны, задачу и риск в одной транзакции.
- Повторное или одновременное преобразование одного тендера возвращает тот же проект.
- Одна AI-рекомендация создаёт одну заявку благодаря уникальному `riskId` и блокировке записи внутри транзакции.
- Номер версии документа вычисляется под блокировкой проекта; два одновременных запроса не получают одинаковую версию.
- `seed` использует upsert и не стирает существующие проекты и тендеры.

## Границы первого этапа

Это готовая инфраструктурная основа с сохранением данных, а не завершённый SaaS. `DEMO_MODE=true` позволяет менять роль без подтверждения личности. Он нужен только для локальной разработки. Отсутствие настоящей авторизации нельзя компенсировать проверкой роли, которую выбирает клиент.

Второй этап заменит `demoContext()` проверенной сессией, свяжет пользователя с компанией и добавит правила чтения данных для ролей. До этого не размещайте демо API в открытом доступе. При `DEMO_MODE=false` бизнес-API возвращают 401.

AI пока имитируется; счётчики дефектов, задач и заявок берутся из базы. Документы сохраняют только метаданные и версии, бинарное хранилище будет реализовано в соответствующем этапе. Фото дефекта временно хранится как ограниченный по размеру raster data URL в PostgreSQL. Приглашения пока только записи базы, без отправки писем и принятия. Полноценные согласования, редактирование компании и offline sync относятся к следующим этапам.

Темы и язык остаются в localStorage. Старое браузерное состояние проектов намеренно не импортируется автоматически; PostgreSQL теперь является единственным источником бизнес-данных.
