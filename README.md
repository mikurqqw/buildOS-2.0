# BuildOS MVP

**Управление компанией:** откройте `/company` под директором: редактирование названия/адреса, назначение ролей, создание и отзыв приглашений по ссылке. Сотрудник открывает `/join#TOKEN` и задаёт пароль. Почтовый сервис не требуется; ссылку директор передаёт самостоятельно. Токен одноразовый, срок 7 дней, хранится только хеш. Смена роли завершает действующие сессии сотрудника; собственную роль директор менять не может. `npm run test:company` проверяет сценарий через HTTP при запущенном приложении.

**Обновление 04.11.2026:** добавлены регистрация компании и вход по БИН/почте/паролю, bcrypt и серверные HttpOnly-сессии. Демо-пользователи из seed не имеют пароля: зарегистрируйте новую компанию. Роль определяется сервером. Подробности и оставшиеся работы: [PROGRESS](docs/PROGRESS.md). Предыдущие разделы документации первого этапа описывают прежний демо-режим; текущие бизнес-API требуют сессию.

Next.js App Router, TypeScript, React, Tailwind, Lucide, PostgreSQL 16 и Prisma. Модульный монолит для строительной компании. Светлая/чёрная темы, русский/казахский/английский; по умолчанию светлая тема и русский язык.

Первый этап — инфраструктурная основа — реализован: интерфейс подключён к PostgreSQL, данные сохраняются на сервере, API проверяет запросы, операции выполняются транзакционно.

## Запуск без Docker

Зависимости, `.env`, миграции и seed на текущем компьютере уже подготовлены. Для нового окружения сначала `npm ci` и `npm run env:setup`.

Первый терминал:

```powershell
npm run db:local
```

Второй терминал:

```powershell
npm run db:prepare
npm run dev
```

Откройте http://localhost:3000. Проверка базы — http://localhost:3000/api/health. База работает на 127.0.0.1:55432 и сохраняется в `.data/postgres`. При повторном запуске данные остаются. Для Docker предусмотрены `compose.yaml`, `db:up`, `db:down` и `db:setup`.

## Проверки

```powershell
npm test
npm run test:integration
npm run typecheck
npm run db:validate
npm run build
```

Интеграционные тесты требуют PostgreSQL с применёнными миграциями. Они проверяют конкурентное преобразование тендера и создание заявки, версии документов, сохранение после переподключения, CHECK-ограничения, межфирменные внешние ключи, 401/403/404/422 API. Тесты создают и удаляют только свои случайные компании.

## Границы

Демо-вход ещё не является настоящей авторизацией: она входит во второй этап. Серверная компания фиксируется в `.env`; `DEMO_MODE=true` разрешает выбирать роль для локальной демонстрации. Перед внешним развёртыванием нужно заменить демо-контекст проверенными сессиями и membership/RBAC. При `DEMO_MODE=false` бизнес-API закрыты.

AI-анализ имитируется, но контекстные счётчики берутся из PostgreSQL. Документы сохраняют пока только метаданные, приглашения не отправляют email, заявки остаются PENDING_APPROVAL. Бинарное хранилище, принятие приглашений, полный цикл дефекта и согласования относятся к следующим этапам ТЗ. Старое браузерное состояние автоматически не переносится в базу; тема и язык остаются в localStorage.

Известный npm audit: 12 advisory (3 moderate, 9 high), совместимые обновления их не устраняют. Перед внешним развёртыванием требуется отдельная миграция затронутых зависимостей. Локальный нативный PostgreSQL запускается через [embedded-postgres](https://github.com/leinelissen/embedded-postgres); Docker остаётся альтернативой.
